# Sprint 03: candidate-specific scientific evaluation

Select a point in the Sample A 3D patch, create C1 if needed, and use **Evaluate C0** and **Evaluate C1** in the Landing Graph. The graph's saved-candidate → scientific-computation → scientific-result branch invokes the backend through Rete's dataflow engine. Its separate editable preview does not run scientific calculations; only committed candidate IDs are evaluated. Duration can be greater than zero and at most 168 hours; sampling steps are 1–360 minutes. C0 and C1 start at their own selected UTC times. A changed start time changes the period being compared, so differences cannot be attributed to observer height alone. Stored evaluations can be selected from each candidate's history.

`POST /api/candidates/{candidate_id}/evaluations` accepts `duration_hours` and `step_minutes`. `GET /api/candidates/{candidate_id}/evaluations` lists persisted results and `GET /api/evaluations/{evaluation_id}` retrieves one. Candidate, requested settings, 720-point horizon, samples, visibility intervals, warnings, errors, provenance and status are stored as immutable SQLite snapshots. Their IDs include the scientific inputs, exact dataset/kernel hashes and result content. Identical reruns are idempotent. Results remain in `data/candidates.sqlite3`; clearing browser local storage only loses the convenience pointer to C0, not the SQLite records.

## Methods and coverage

The existing `lunar_core.horizon.horizon_mask` is run at the **candidate coordinates** and observer height, with 0.5° azimuth increments, near 20 m spacing below 8 km, and far 240 m spacing from 8 km to just under 200 km. Before invoking it, the application independently generates the exact ray sample positions used by that routine and rejects the evaluation if *any* bilinear sample is out of coverage or non-finite. This is necessary because the upstream horizon routine otherwise ignores NaNs. This check covers the discrete samples, not terrain between rays. The original Sample A near window is only ±8.5 km, so many locations selectable on the ±6 km patch cannot support a complete 8 km near-field horizon. Their evaluation is `UNAVAILABLE`; no flat horizon is substituted. To try the supplied data, click near the original site pin at the patch center.

The near and far source products are LDEM_80S_20MPP_ADJ (20 m) and LDEM_60S_240MPP_ADJ (240 m). The source URLs, local NPZ SHA-256, resolution and kernel SHA-256 are recorded per evaluation. The original NASA GeoTIFFs were inspected with Rasterio and both report NaN nodata. The downloaded NPZ windows contain floating arrays without a separate stored mask; non-finite bilinear samples are rejected. Hashes identify local windows, not complete upstream GeoTIFFs. Candidate near-window hash and source must match the current file, and SPICE file hashes must match those loaded at API startup. Changing them requires restarting the API. The SPICE lunar radii are checked against the 1,737,400 m DEM reference sphere.

SPICE uses `lunar_core.geometry.horizontal_positions`, MOON_ME (DE421), LT+S, and no refraction. The observer is at the candidate planetocentric latitude/east longitude with height above the reference sphere equal to sampled DEM elevation **plus** observer height above ground. This explicitly differs from the older catalog analysis, which passes only observer height to its SPICE `SurfacePoint`. Horizon ground elevation is separately sampled from the DEM by the existing routine. Sun visibility uses the upper limb against the interpolated terrain horizon; Earth uses its center with zero additional clearance. Simultaneous visibility is their Boolean intersection.

Samples start at the candidate UTC time over `[start, end)`. The existing `build_windows` groups each sample until the next, with the final interval clipped to the requested end. Boundaries have up to one sampling-step uncertainty; intervals touching the requested range edges are marked truncated. Duration is the sum of visible sampled intervals. Results are geometric estimates, not communication performance, solar-power analysis, mission suitability or landing safety.

## Scientific verification record

- Sprint 02 baseline: 115 backend and 45 frontend tests passed.
- Existing JPL Horizons golden tests exercise the upstream SPICE geometry, with their stated 1 arcsecond tolerance; they do not independently validate every candidate-specific terrain/observer configuration.
- Existing analytic tests compare a flat-sphere horizon and isolated mountain with geometric expectations. New tests check selected coordinates and heights passed into the horizon and SPICE dependencies, sample and interval boundaries, coverage and NaN refusal, multiple persisted evaluations, and real LOLA/SPICE C0/C1 execution where data is available.
- A browser run selected a point at approximately 89.503387°S, 0.190381°E and obtained `COMPUTED_UNVERIFIED` for both candidates. With 168 h windows and 60 min steps, C0 began 2026-11-07 and C1 began 2026-11-23; therefore the displayed differences reflect **both time and height changes**, not a controlled height experiment. The C1 run reported 167 h Sun, 157 h Earth and 156 h simultaneous sampled visibility. These are demonstration outputs, not independently validated values or operational claims.
- An earlier point at approximately 89.481661°S, 3.171006°E returned `UNAVAILABLE`: 890 of 287,280 near-field horizon samples lacked coverage. Both computed and unavailable results survived browser reload in the tested local session.
- Sprint 02's separate Rasterio/pyproj comparison remains bounded evidence for five points, not a general validation of this calculation.

`COMPUTED_UNVERIFIED` means the numerical workflow ran, not that its result was independently scientifically validated. `UNAVAILABLE` is used for missing/mismatched inputs or incomplete sampled coverage; `ERROR` is an execution failure. The API reserves `VALIDATED` but this sprint never assigns it. Error and warning details appear in the validation inspector. Existing upstream credits and licenses remain intact.
